# 信頼性・スケール設計

## AI Provider障害

対策:
- AIを非同期ジョブ化
- リトライ
- タイムアウト
- Dead Letter Queue
- Provider Adapter
- AI停止中も既存データ閲覧可能

## 情報源障害

対策:
- ソース単位で独立ジョブ
- 失敗履歴
- 再試行
- 前回取得データ保持
- 最終取得日時表示

## AIコスト増大

対策:
- ルールフィルタを先に実行
- キャッシュ
- 同一公募の再解析防止
- 用途別モデル
- バッチ処理

## 1万団体想定

悪い構成:
10,000団体 × 10,000公募を毎回AI処理

良い構成:
新規/更新公募
→ DBルールフィルタ
→ 候補団体のみ抽出
→ AI詳細判定
→ 通知

処理単位を「全団体」ではなく「新規/更新された公募と候補集合」にする。

## 即時性

即時性はAIの常時自走ではなく、自社の監視パイプラインで担保する。

Source polling/event
→ Change detection
→ Queue
→ Normalize
→ Match
→ Notify

MVPではこのパイプラインの実測遅延を計測し、後からSLAを定義する。

## 冪等性

同じ公募を何度取得しても、
- 二重登録しない
- 二重通知しない
- 不要な二重AI実行をしない

ことを必須とする。
